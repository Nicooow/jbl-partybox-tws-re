# 0x010C — stream/link-config confirmation (two-sided handshake)

BESAUD command `0x010C` is the **confirmation half of the stream-configuration handshake**. It
appears on the wire in **both directions of a request/response pair**: one side emits it as a
*command* (`0x80`) with a 2-second ack wait, the other side answers with the same cmd id over the
*ack channel* (`0x81`). It is tied to the 0x0106/0x0107 configuration exchange: bit 6 of the event
flag register is set when 0x0106/0x0107 is received and cleared once the `0x010C` confirm comes
back. There are **three producers** — one `0x80` initiator and two `0x81` responder paths.

* Firmware: `extracted/payload_1.bin` (BES2000IK), Thumb, load base `0x3C000000`. File offset = VA − `0x3C000000`. Aliased at `0x0C000000` (Δ `0x30000000`).
* `ctx = 0x2002F31C` (literal `iRam3c01a508` / `_DAT_3c01a120` / `_DAT_3c01968c`).
* Envelope: `[type][cmd16 LE][payload…]`, type `0x80`=command / `0x81`=ack.
* Evidence status: **static RE only.**

## Producers

### (1) `FUN_3c01a058(void)` — file `0x1A058` — *initiator*, type `0x80`

```c
uStack_1c = 0x10c;  uStack_18 = 0;  uStack_14 = 0;  uStack_10 = 0;  uStack_c = 0;
iVar1 = FUN_3c019fe0(&uStack_1c, 0x12, 2000);   /* cmd 0x010C, wait ≤2000 ms */
if (iVar1 == 0) FUN_3c04101c(6);                /* ack received → clear event bit 6 */
```

Constant frame (19 bytes on the wire: `80 0C 01 00×16`). It **blocks** up to 2000 ms waiting for
the peer's `0x81`; a return of `0` means the ack arrived, in which case it clears pending flag
bit 6 (`FUN_3c04101c(n)` clears bit `n` of the global event register `*_DAT_3c041040`).

### (2) `FUN_3c01a0f0(int param_1)` — file `0x1A0F0` — *responder*, type `0x81`

```c
uStack_24 = 0x10c;  uStack_22 = 0;
FUN_3c01a08c(&uStack_24, 0x12);                 /* sent through the ACK channel → type 0x81 */
if (param_1 != 0)
  FUN_3c018808(*(u32*)(ctx + 0x308), 0);        /* re-arm TWS link scheduling */
```

`FUN_3c01a08c` prepends the ack type byte `0x81`, so this is the *reply* to an inbound `0x010C`,
not a fresh command. It does not wait for anything (a reply is not itself acknowledged). When
`param_1 != 0` it additionally calls `FUN_3c018808(session, 0)` — a TWS **link/role scheduler**
that compares the connected peer's ACL with `ctx+0x308` and re-arms timing globals (values
`10`/`0x28`/`0x32`/`0x10`). Only the cmd16 is written into the 18-byte buffer; the rest is stack
remnant on this path.

### (3) Inbound handler `parse_cmd` case @ `0x3C01A468`

```c
case 0x10c:
  *(char*)(ctx + 0x291) = 1;                 /* arm "0x010C reply pending" */
  FUN_3c019628(*(code**)0x3C01A538);         /* = FUN_3c01a0f0 (pool word 0x0C01A0F1) */
  FUN_3c04101c(6);                           /* clear event bit 6 */
  return;                                    /* NOTE: no generic ack is sent */
```

The handler deliberately does **not** fall through to the shared `0x81` tail — the reply is
produced by the callback (producer 2) instead.

## The callback / pointer table driving them

Both producers are reached **only through `parse_cmd`'s literal pool** (there is no `BL` to them
anywhere in the image); the bounded pointer scan found exactly these references:

| stored at (VA) | value | used as |
|---|---|---|
| `0x3C01A6A8` | `0x0C01A058` (pool word `uRam3c01a6a8`) | `FUN_3c013350(0, 0, uRam3c01a6a8)` at `code_r0x3c01a5d2` (end of **case 0x0106** and **case 0x0107**) → posts app event `0x17`, whose event-loop handler calls the pointer → **`FUN_3c01a058(0,0)`** |
| `0x3C01A8A0` | `0x0C01A058` (pool word just before the RX dispatcher) | a second indirect reference in the RX-dispatcher region |
| `0x3C01A538` | `0x0C01A0F1` (pool word `uRam3c01a538`) | `FUN_3c019628(uRam3c01a538)` in **case 0x010C** → registers/invokes **`FUN_3c01a0f0`** |

So the "table" is two pool slots inside `parse_cmd`:
* slot `0x3C01A6A8` → the **send** routine (`FUN_3c01a058`), dispatched via event `0x17`
  (`FUN_3c013350` builds the message, event-loop `case 0x17` does `(*(code*)msg[1])(msg[2],msg[3])`).
* slot `0x3C01A538` → the **reply** routine (`FUN_3c01a0f0`), handed to `FUN_3c019628`.

### `FUN_3c019628(code *cb)` — file `0x19628`

```c
iVar5 = *(int*)(ctx + 0x28c);                 /* the peer link object */
if (iVar5 == 0) { ctx+0x291 = 0; if (cb) return (*cb)(1); }
else if (*(char*)(iVar5 + 0x22) == 3) {       /* link object suspended */
    FUN_3c040ff4(5);                          /* set event bit 5 */
    if (*(char*)(ctx + 0x291) != 0) {         /* reply still pending? */
        *(code**)(ctx + 0x2d0) = cb;          /*   store it for later */
        func_0x3c01fcc8(iVar5); FUN_3c01f8d0();
        ... software_interrupt(0); return *(code**)(ctx + 0x2d8);
    }
}
else { ctx+0x291 = 0; if (cb) return (*cb)(1); }
return pcVar3;
```

It either **calls the reply immediately** with argument `1` (no link object, or object not in the
"suspended" state 3) — which makes `FUN_3c01a0f0(1)` send the reply *and* re-arm the scheduler —
or **stores it at `ctx+0x2d0`** and triggers an SVC (yield/resume) for the suspended object.

## Why two send paths / different timeouts

| | producer 1 (`FUN_3c01a058`) | producer 2 (`FUN_3c01a0f0`) |
|---|---|---|
| wire type | `0x80` command (via `FUN_3c019fe0`) | `0x81` ack (via `FUN_3c01a08c`) |
| timeout | **2000 ms** ack wait | none (a reply is not acked) |
| role | handshake **initiator** (after 0x0106/0x0107 rx) | handshake **responder** (after 0x010C rx) |
| side effect on ok | `FUN_3c04101c(6)` — clear "config confirm pending" | `FUN_3c018808(session,0)` if `param_1 != 0` — re-arm link scheduling |
| scheduled by | event `0x17` (`FUN_3c013350`) from `parse_cmd` 0x0106/0x0107 | direct callback from `FUN_3c019628` (case 0x010C) |

The 2000 ms wait exists because producer 1 must observe the peer's confirmation; the responder
just emits the confirmation, so it needs no wait. Note bit 6 is **set** by the 0x0106/0x0107
handlers (`FUN_3c040ff4(6)`) and **cleared** on both sides of the `0x010C` exchange.

## `ctx` fields

* **`ctx+0x291`** — a one-shot **"0x010C reply pending"** flag. Set to `1` by the inbound
  `0x010C` handler; consumed (and cleared) by `FUN_3c019628`, which uses it to decide between
  deferring the reply (store at `ctx+0x2d0`) and calling it immediately.
* **`ctx+0x28c`** — the peer link object; `object+0x22 == 3` means "suspended" (same test used by
  the 0x0107 handler and by `FUN_3c019628`).
* **`ctx+0x2d0` / `ctx+0x2d8`** — deferred-callback slots populated by `FUN_3c019628`.
* **`ctx+0x308`** — the connection/profile object passed to `FUN_3c018808`.
* Event register `*_DAT_3c041040` — bits set by `FUN_3c040ff4(n)`, cleared by `FUN_3c04101c(n)`;
  bit 6 is the "awaiting 0x010C confirm" bit.

## Confidence & unknowns

**Confident:**
* Producer (1) sends `80 0C 01 00×16`, waits 2000 ms, and on success clears event bit 6.
* Producer (2) replies `81 0C 01 …` through `FUN_3c01a08c` and calls `FUN_3c018808(session,0)`
  iff `param_1 != 0`.
* The inbound case sets `ctx+0x291 = 1`, calls `FUN_3c019628(&FUN_3c01a0f0)`, clears bit 6, and
  returns **without** emitting the generic ack.
* Pointer scan: `FUN_3c01a058` is referenced only at `0x3C01A6A8`/`0x3C01A8A0` (pool words) and
  `FUN_3c01a0f0` only at `0x3C01A538` (pool word `0x0C01A0F1`).

**Inferred (labelled):**
* `0x010C` is the **stream/link-config confirmation** exchanged after 0x0106/0x0107; event bit 6
  tracks "config sent, confirm outstanding". Corroborated by the fact that both 0x0106 and 0x0107
  set bit 6 (`FUN_3c040ff4(6)`) and both schedule the `0x010C` sender.
* `ctx+0x291` = "reply pending"; `FUN_3c019628` defers the reply while the link object is suspended
  (state 3) by storing it at `ctx+0x2d0` and yielding.

**Unknown / not verified:**
* The precise application meaning of the `0x010C` handshake (which stream property it confirms)
  is not spelled out by any string; it is inferred from the 0x0106/0x0107 coupling and event bit 6.
* The bodies of the deferred-callback slots (`ctx+0x2d0`/`ctx+0x2d8`) and `FUN_3c018808`'s full
  scheduling semantics were not decompiled in depth (called once, bounded).
* `FUN_3c040ff4(5)` inside `FUN_3c019628` (a second event bit) is used but its semantic is not
  resolved.

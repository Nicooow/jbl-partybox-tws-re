# 0x010A — TWS_BESAUD_CMD_SYNC_REM_KEY_STATUS (remote-key status sync)

BESAUD command `0x010A` carries the **remote key status** between the two TWS peers. The
payload is a **u32 key id** followed by a **1-byte flag**, so the message is small but
semantically the richest of the three frames here: on receive the key id and flag are turned
into a local key injection (`FUN_3c01e954` → callback `0x3C01C32D` → `FUN_3c01c13c`), and one
magic key id (`8`) additionally sets a global latch. The firmware logs the literal string
`"TWS_BESAUD_CMD_SYNC_REM_KEY_STATUS"` when the frame arrives.

* Firmware: `extracted/payload_1.bin` (BES2000IK), Thumb, load base `0x3C000000`. File offset = VA − `0x3C000000`. Same bytes aliased at `0x0C000000` (Δ `0x30000000`; `0x0C01xxxx` == `0x3C01xxxx`).
* Shared context struct: `ctx = 0x2002F31C` (literal `1cf30220` at `0x3C01A508`).
* Frame envelope: `[type][cmd16 LE][payload…]`; `0x80`=command, `0x81`=ack/response. Payload length fixed at `0x12` (18) by the builder.
* Evidence status: **static reverse engineering only** (not yet live-injected). Addresses are VA unless "file 0x" is stated.

## Wire format

### Outbound — speaker → peer (builder `FUN_3c01afd4`)

The builder assembles an 18-byte local buffer (`cmd16` + payload), then the generic sender
`FUN_3c019fe0` prefixes the transport type byte `0x80`. Total on the wire = **19 bytes**.

| offset | size | field | value / semantics |
|---|---|---|---|
| 0 | 1 | type | `0x80` — command (written by `FUN_3c019fe0`) |
| 1 | 2 | cmd16 (LE) | `0A 01` = `0x010A` |
| 3 | 4 | key id (LE u32) | `*(u32*)param_1` — the remote key id (see *Received side*) |
| 7 | 1 | flag | low byte of `*(u16*)(param_1 + 1)` — press/release/status flag |
| 8 | 11 | padding | `0x00` |

Map to the builder's stack: buffer base = `&uStack_24`; `uStack_24=0x010A`,
`uStack_22/uStack_20` = low/high halves of the key u32 (`*param_1`), `uStack_1e` = flag byte
(`*(u8*)(u16*)(param_1+1)`), `uStack_1d=0`, `uStack_1c/uStack_18/uStack_14=0`.

### Inbound — peer → speaker (handler `parse_cmd` case `0x010A` @ `0x3C01A428`)

| offset | size | field | value / semantics |
|---|---|---|---|
| 0 | 1 | type | `0x80` (routed as a *command* by the RX dispatcher) |
| 1 | 2 | cmd16 (LE) | `0A 01` = `0x010A` |
| 3 | 4 | key id (LE u32) | read as `*(int*)(param_1 + 1)`; **compared against `8`** |
| 7 | 1 | flag | read as `*(u8*)(param_1[3])`; passed on as a byte |
| 8 | 11 | padding | ignored |

Handler body (`0x3C01A428`):

```c
case 0x10a:
  FUN_3c04cb98(0x3C04FD54, 0x3C050974, 0x3C0508BC, 0x27d);   /* log tag + line 637 */
  FUN_3c04cb98(0x3C0509A0);          /* "TWS_BESAUD_CMD_SYNC_REM_KEY_STATUS" */
  FUN_3c04cb98(0x3C04D60C);
  key  = *(int *)(param_1 + 1);      /* u32 at payload+2 */
  flag = param_1[3];                 /* u16 at payload+6 */
  if (key == 8) *puRam3c01a6ac = 1;  /* global latch 0x200331D4 = 1 */
  FUN_3c01e954(4, key, (char)flag, 0x3C01C32D);
  break;   /* → generic 0x81 ack */
```

**Reply.** Like every BESAUD command, receipt triggers the generic 18-byte ack from
`FUN_3c01a08c` (type `0x81`, body = the stack buffer whose first 2 bytes echo `0x010A`). The
`case` falls through to the shared ack tail `LAB_3c01a26e`.

## Emitted side

**Builder:** `FUN_3c01afd4(undefined4 *param_1)` (file `0x1AFD4`):

```c
uStack_1d = 0;
uStack_22 = (u16)*param_1;                 /* key low 16  */
uStack_20 = (u16)(*param_1 >> 0x10);       /* key high 16 */
uStack_1e = (u8)*(u16 *)(param_1 + 1);     /* flag        */
uStack_1c = uStack_18 = 0; uStack_14 = 0;
uStack_24 = 0x10a;
FUN_3c019fe0(&uStack_24, 0x12, 1000);      /* buf, len=18, timeout_ms=1000 */
```

**Trigger (internal app event `0x14`).** The app event loop `FUN_3c012e84` (file `0x12E84`),
message queue `ctx+0x31C`, has:

```c
case 0x14:
  iStack_24  = puVar5[1];                                       /* key = msg word 1           */
  puStack_20 = CONCAT22(puStack_20._2_2_, (ushort)*(byte*)(puVar5 + 2)); /* flag = byte at msg+8 */
  FUN_3c01afd4(&iStack_24);
  break;
```

So the builder's two inputs come straight from the event-`0x14` message: **key** = the u32 at
message word 1 (`puVar5[1]`), **flag** = the byte at message offset 8 (`*(byte*)(puVar5+2)`),
which the loop packs into the low 16 bits of the second stack word. The *poster* of event
`0x14` (i.e. which local key event originally produced the key id) is not among the named
files; the message-queue poster is outside the reviewed set.

Transmission gating is in `FUN_3c019fe0`: it returns `-1` (no-op) while the TWS/SPP session
handle `*(u32*)(ctx+0x310) == 0`; otherwise it writes `0x80`, copies the 18 bytes and, when a
peer ack wait is configured, awaits the reply up to `timeout_ms` (1000 ms).

## Received side

**Handler:** `parse_cmd = FUN_3c01a1f4` (file `0x1A1F4`). `TBH` base `0x3C01A20E` (`base =
TBH_addr + 4`), index `cmd16 − 0x100`; `0x010A` (index 10) → `0x3C01A428` (shown above).

**Remote-key path — `FUN_3c01e954` (file `0x1E954`).** It does **not** inject the key
directly; it builds a 5-word descriptor on the stack and hands it to the lower dispatcher
`FUN_3c0436d0`:

```c
void FUN_3c01e954(a, b, c, d) {           /* called as (4, key, flag, 0x3C01C32D) */
  uStack_1c = 3;      /* descriptor type / class */
  uStack_18 = a;      /* = 4  (op / kind)        */
  uStack_14 = d;      /* = 0x3C01C32D callback   */
  uStack_10 = b;      /* = key id                */
  uStack_c  = c;      /* = flag                  */
  FUN_3c0436d0(auStack_24);   /* auStack_24[8] header immediately precedes the 5 words */
}
```

i.e. the message posted upward is `{hdr[8], 3, 4, 0x3C01C32D, key, flag}`.

**Callback `0x3C01C32D`** (Thumb pointer `0x3C01C32C | 1`, file `0x1C32C`) — a small logging
trampoline. Disassembly:

```
0x3C01C32C  push {r3,r4,r5,lr}
0x3C01C32E  ldr  r2,[pc,#0x2c]     ; log-tag string   (0x3C2EFA54)
0x3C01C330  mov  r5,r0             ; r5 = key
0x3C01C332  mov  r4,r1             ; r4 = flag
0x3C01C334  movw r3,#0x37b         ; line 891
0x3C01C33C  bl   0x3C04CB98        ; log(...)  (2 more log calls: key / flag)
0x3C01C350  mov  r0,r5
0x3C01C352  uxtb r1,r4             ; r1 = flag & 0xFF
0x3C01C358  b.w  0x3C01C13C        ; tail-call the real injector FUN_3c01c13c(key, flag)
```

So `0x3C01C32D` = "log the remote-key event, then hand `(key, flag&0xFF)` to
`FUN_3c01c13c`", the actual remote-key injection routine (not among the named files).

**Special key value `8`.** If the u32 key id equals `8`, the handler first sets the global
byte/word at RAM **`0x200331D4`** (literal `0x3C01A6AC`) to `1`. No reader of `0x200331D4` is
present in the named files, so its effect is not observable statically — the value `8` is a
distinct/reserved key status (a sentinel or a dedicated key) rather than an ordinary key id,
because it is singled out before dispatch.

**Key id / flag semantics.** The key id is the same numeric space as the local key ids
(logged as `TWS_BESAUD_CMD_SYNC_REM_KEY_STATUS` and fed to a generic key injector), and the
flag is a 1-byte press/release (or key-event-type) discriminator. The exact flag encoding
(1=press / 0=release vs. an event enum) is **inferred**, not proven by these files.

## Confidence & unknowns

**Confident (direct code + constant evidence):**
* Outbound frame = `80 0A 01 | key(4 LE) | flag | 00×11` (19 bytes); key from event-`0x14`
  message word 1, flag from message byte 8.
* Inbound reads u32 key at payload+2 and byte flag at payload+6, logs
  `"TWS_BESAUD_CMD_SYNC_REM_KEY_STATUS"`, sets `0x200331D4=1` when key `== 8`, and calls
  `FUN_3c01e954(4, key, flag, 0x3C01C32D)`.
* `FUN_3c01e954` posts the 5-word descriptor `{3,4,0x3C01C32D,key,flag}`; `0x3C01C32D` is a
  Thumb callback that logs and tail-calls `FUN_3c01c13c(key, flag)`.
* `ctx = 0x2002F31C` for every function here.

**Inferred (labelled as such):**
* The 1-byte field at payload+6 is a **press/release** (or key-event type) flag; the encoding
  is not proven.
* Key id `8` is a reserved/special status; `0x200331D4` is a latch whose effect is invisible
  in the named files.

**Unknown / not verified:**
* Poster of app event `0x14` (the origin of the emitted key id) — outside the named files.
* Readers of `0x200331D4` and the concrete effect of key id `8`.
* Bodies of `FUN_3c0436d0` and `FUN_3c01c13c` (not reviewed here).
* Ack body for `0x010A` — the generic tail writes only the 2-byte cmd16 echo; the remaining 16
  ack bytes are uninitialised stack remnants on this path.

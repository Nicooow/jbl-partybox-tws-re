# 0x0110 — TWS stereo-channel assignment (active-only variant), twin of 0x0108

BESAUD command `0x0110` is the **second** of the two "assign the TWS Left/Right channel"
messages. On the wire it is a 1-byte-mode payload exactly like `0x0108`; on the **receive**
side it is **byte-for-byte identical** to `0x0108` (same map into `ctx+0x19`). The only real
difference is on the **emit** side: the builder logs the channel and commits **only `ctx+0x19`**
(never `ctx+0x18`), and does so **before** the send. `0x0108` is the *committed* variant that
also updates `ctx+0x18`.

* Firmware: `extracted/payload_1.bin` (BES2000IK), Thumb, load base `0x3C000000`. File offset = VA − `0x3C000000`. Aliased at `0x0C000000` (Δ `0x30000000`).
* Shared context struct: `ctx = 0x2002F31C` (literal at `0x3C01A508`, `0x3C01AF0C`).
* Frame envelope: `[type][cmd16 LE][payload…]`; `0x80`=command, `0x81`=ack. Typical fixed payload 18 bytes.
* Evidence status: **static reverse engineering only**.

## Shared helpers (verified from the image)

`FUN_3c015b18(mode)` is a **one-argument debug logger** (`0x3C015B18`): compares **r0** to 3, 4, 2
and tail-calls `uart_printf` (`FUN_3c041b2c`).

| r0 (mode) | string | literal VA |
|---|---|---|
| `2` | `"\r\nTWSLR=S\r\n"` | `0x3C04FAB8` |
| `3` | `"\r\nTWSLR=L\r\n"` | `0x3C04FAA0` |
| `4` | `"\r\nTWSLR=R\r\n"` | `0x3C04FAAC` |

`r1` is **never read** by this function. `ctx = 0x2002F31C`.

## Wire format

### Outbound — builder `FUN_3c01aed4` (file `0x1AED4`)

| offset | size | field | value / semantics |
|---|---|---|---|
| 0 | 1 | type | `0x80` (written by `FUN_3c019fe0`) |
| 1 | 2 | cmd16 (LE) | `10 01` = `0x0110` |
| 3 | 1 | payload[0] | mode byte, raw (no remap) |
| 4 | 15 | padding | all `0x00` |

Total 19 bytes.

### Inbound — handler `parse_cmd` case `0x0110` @ `0x3C01A4C8` (and inlined copy in `FUN_3c01a8a8`)

| offset | size | field | value / semantics |
|---|---|---|---|
| 0 | 1 | type | `0x80` |
| 1 | 2 | cmd16 (LE) | `10 01` = `0x0110` |
| 3 | 1 | payload[0] | mode byte, read as `(char)param_1[1]` |
| 4 | 15 | padding | ignored |

**Reply.** `break` → generic `0x81` ack via `FUN_3c01a08c(buf, 0x12)` with cmt16 echo `10 01`.

## Emitted side (builder `FUN_3c01aed4`)

```c
void FUN_3c01aed4(undefined4 param_1) {
  buf[3..17] = 0;
  *(u8*)(ctx + 0x19) = (byte)param_1;          /* commit BEFORE the send; ctx+0x18 NOT touched */
  buf[0..1] = 0x0110;  buf[2] = (byte)param_1;
  func_0x3c015b18(param_1, 0xb);               /* → prints TWSLR=S/L/R ; r1 = 0xb is inert */
  FUN_3c019fe0(buf, 0x12, 1000);               /* send 18 bytes, 1000 ms (needs ctx+0x310 != 0) */
}
```

Disassembly (`0x3C01AED4`): `push {r4,r5,lr}` → `ldr r5,[pc,#0x34]` (`r5 = ctx`) →
`movs r1,#0xb` → `mov.w r4,#0x110` → `strb r0,[r5,#0x19]` (ctx+0x19 = param_1) →
`strb.w r0,[sp,#6]` (payload[0]) → `strh.w r4,[sp,#4]` (cmd `0x0110`) → `bl 0x3c015b18` →
`bl 0x3c019fe0`. Note there is **no** `strb …,[…,#0x18]`.

**Trigger (internal app event `0x1A`).** Event loop `FUN_3c012e84`:

```c
case 0x1a:  FUN_3c01aed4(*(undefined1 *)(puVar5 + 1));  break;   /* event id 0x1A */
```

The emitted mode byte is the first data byte of queued message `0x1A`.

## Received side (case `0x0110`)

```c
case 0x110:
  if ((char)param_1[1] == 3)      *(u8*)(ctx + 0x19) = 4;
  else if ((char)param_1[1] == 4) *(u8*)(ctx + 0x19) = 3;
  else                            *(u8*)(ctx + 0x19) = 2;
  func_0x3c015b18(*(u8*)(ctx + 0x19), 3);                    /* r1 = 3 inert */
  break;   /* → generic 0x81 ack */
```

### Wire byte ↔ internal value ↔ channel name

| wire payload[0] | stored `ctx+0x19` | prints | channel |
|---|---|---|---|
| `3` | `4` | `TWSLR=R` | Right |
| `4` | `3` | `TWSLR=L` | Left |
| `2` (and all others) | `2` | `TWSLR=S` | Stereo |

## PROOF: 0x0108 vs 0x0110 — exhaustive difference list

### Inbound bodies are byte-identical

`parse_cmd` `case 0x0108` and `case 0x0110` are the **same source text** — same test
(`(char)param_1[1]`), same map (`3→4, 4→3, else→2`), same target field (`ctx+0x19`), same
logging call `func_0x3c015b18(*(u8*)(ctx+0x19), 3)`, same `break`. The inlined copies in the
RX dispatcher `FUN_3c01a8a8` are likewise identical to each other (they read the raw frame via
`pcVar21[3]` instead of `param_1[1]`, which is the same payload byte). **No receiver can tell
the two commands apart.**

### Builders differ in exactly four ways

| property | `FUN_3c01ae28` (`0x0108`) | `FUN_3c01aed4` (`0x0110`) |
|---|---|---|
| cmd16 | `0x0108` | `0x0110` |
| `ctx` fields committed | `ctx+0x18` **and** `ctx+0x19` | `ctx+0x19` **only** |
| commit timing | **after** `FUN_3c019fe0` | **before** `FUN_3c019fe0` |
| logger r1 (inert) | `8` | `0xb` |
| prologue / frame | `push {r4,lr}` + `sub sp,#0x18` | `push {r4,r5,lr}` + `sub sp,#0x1c` (keeps `ctx` in r5) |
| payload value written | raw `param_1` | raw `param_1` |
| `FUN_3c019fe0(buf,0x12,1000)` | identical | identical |

Everything else (payload layout `[cmd16][mode][00×15]`, the raw value on the wire, the log
selector, the send call) is the same.

### What the differences mean

* On the **wire** and at the **receiver**, `0x0108` and `0x0110` are the *same* operation
  ("set the peer's TWS channel from this mode byte"). The peer cannot distinguish them.
* The distinction is purely **local bookkeeping on the sender**:
  * `0x0108` re-commits the channel into **both** channel slots (`ctx+0x18` = configured copy,
    `ctx+0x19` = active copy) — a *committed/negotiated* assignment.
  * `0x0110` updates **only the active slot** `ctx+0x19` — an *active-only* change.
* The `8` / `0xb` logger arguments are inert (see `0x0108.md`, *Answer 4*): `FUN_3c015b18`
  reads only r0 and tail-calls the variadic `uart_printf`, which ignores the extra argument.
  They do **not** encode the command id (note `0x08` matches but `0x0b ≠ 0x10`), so they are
  not a meaningful tag.

Working model: the two commands are a versioned/paired pair of the same "channel assign"
operation, kept as separate BESAUD ids for compatibility, where `0x0108` was later extended to
also persist the value into the negotiated slot `ctx+0x18`.

## Confidence & unknowns

**Confident (direct code + constant evidence):**
* Inbound `0x0108` and `0x0110` are byte-identical: same map `3→4, 4→3, else→2` into `ctx+0x19`, then log.
* Outbound `0x0110` frame is `80 10 01 | v 00×15`; `v` raw; send gated on `ctx+0x310 != 0`.
* `FUN_3c01aed4` commits **only** `ctx+0x19` (before the send); `FUN_3c01ae28` commits `ctx+0x18` **and** `ctx+0x19` (after the send).
* The differing logger second argument (`8`/`0xb`) is never read by `FUN_3c015b18`.

**Inferred (labelled):**
* `0x0108` = committed/negotiated channel set (updates `ctx+0x18`); `0x0110` = active-only set.
* `ctx+0x18` = configured copy (also fed by inbound `0x0101`), `ctx+0x19` = active copy.

**Unknown / not verified:**
* Not live-injected; the "why two ids" question (firmware-pairing/legacy vs. genuinely different app semantics) is unresolved from static code alone.
* Consumers of `ctx+0x18`/`ctx+0x19` were not located (write-only in this function set).
* Whether a peer ever emits `0x0110` in practice (vs. `0x0108`) is unknown.

# 0x0107 — audio-stream configuration / codec setup

BESAUD command `0x0107` is the **stream-configuration** frame: the richest payload of the
BESAUD command set. It announces the audio-stream parameters (mode/selector, channel
selector, codec/capability word, and a stream config word whose **high 16 bits carry the
sample rate** — `0xAC44` = 44100 observed at byte offset 12). The receive handler is also
the only place where the local volume is (re)applied during stream bring-up.

* Firmware: `extracted/payload_1.bin` (BES2000IK), Thumb, load base `0x3C000000`. File offset = VA − `0x3C000000`. Aliased at `0x0C000000` (Δ `0x30000000`).
* Shared context struct: `ctx = 0x2002F31C` (literal `0x3C01AE24` = `0x2002F31C`).
* Frame envelope: `[type][cmd16 LE][payload…]`; `0x80`=command, `0x81`=ack.
* Evidence status: **static reverse engineering only**.

## Wire format — complete field map

### Outbound — speaker → peer (builder `FUN_3c01ad94`, 18-byte buffer)

Exact stack stores (disassembly-confirmed; buffer base `sp+4`, i.e. buf offset = `sp`−4):

| buf off | size | field | source |
|---|---|---|---|
| 0 | 2 | cmd16 (LE) `0x0107` | `strh.w r0,[sp,#4]`, `r0=0x107` |
| 2 | 1 | **mode / selector** | `strb r6,[sp,#6]` = `param_1` (`1`, `2`, or other) |
| 3 | 1 | **param_2** | `strb fp,[sp,#7]` |
| 4 | 1 | **param_3** | `strb sl,[sp,#8]` |
| 5 | 1 | **param_4** | `strb sb,[sp,#9]` |
| 6 | 1 | 0 | unset (padding) |
| 7 | 1 | **channel/mode byte** `uVar3` | `strb r5,[sp,#0xb]` |
| 8 | 1 | **param_5** (level/ch-count) | `strb r8,[sp,#0xc]` (`ldrsb` of the 5th arg) |
| 9 | 1 | **state flag** | `strb r3,[sp,#0xd]` = `1`/`2` (see below) |
| 10 | 4 | **config word B** = `param_7` | `str.w r3,[sp,#0xe]`, `r3=[sp+0x48]` |
| 14 | 4 | **config word A** = `param_6` | `str.w r7,[sp,#0x12]`, `r7=[sp+0x44]` |

**Channel/mode byte `uVar3` (buf[7])**:

```
param_1 == 1  :  uVar3 = (*(u8*)(ctx+0x18) == 2) ? 2 : 3
param_1 == 2  :  uVar3 = 4
otherwise     :  uVar3 = 2
...
*(u8*)(ctx+0x18) = uVar3          /* written AFTER the send */
```
(`ctx+0x18` is the persisted channel selector; the 0x0101 handler also writes it: `3→4`,
`4→3`, else `2`.)

**State flag (buf[9])** — `uStack_33`:
```
if (func_0x3c01ca78(3) != 0)  flag = 1;      /* current state == 3 */
else if (func_0x3c01ca78(9) != 0) flag = 2;  /* current state == 9 */
else flag = 0;
```

**Sample rate** lives in config word B (`param_7`, bytes `[10..13]`): its **high half**
(bytes `[12..13]`) is the sample rate as **u16 LE**, e.g. `44 AC` = `0xAC44` = 44100 Hz.
(Confirmed offset **12**.) The low half (`[10..11]`) is the companion config (e.g. bitrate/format).

## `ctx+9` states and their asymmetry (0x0107 view)

| `ctx+9` | role model | inbound 0x0107 behaviour |
|---|---|---|
| `1` | initiator / master | configures the active stream object (`ctx+0x28c`, `+0x22==3` = active): pushes byte `[5]` via `func_0x3c01fa58`, applies volume, then `FUN_3c040ff4(6)` + optional `FUN_3c01dc64(1)`; **does not** store config word A |
| `2` | follower | writes byte `[3]` into `ctx+0x300`/`ctx+0x301`, applies volume, and **stores config word A** (bytes `[14..17]`) into the global via `func_0x3c01c7b0` |
| other | transitional | only volume + ack |

So the two roles each consume a **different subset** of the frame: the master drives the
stream object; the follower stores the peer's config word A.

## What `FUN_3c01a124` and `FUN_3c01c7b0` do

**`FUN_3c01a124(param_1=(char)byte[2], param_2=byte[5], param_3=u32@[10..13])`** (file `0x1A124`)
is the same **compatibility/arbitration gate** used by `0x0106`. It validates the announced
mode/marker/config word against the active stream object `*(int*)(ctx+0x28c)` (whose `+0x22 == 3`
means "stream active") and global `*(u32*)0x2002ABE0` (`func_0x3c043958`). Returns:

| ret | meaning | side effect |
|---|---|---|
| `1` | compatible / no change | `FUN_3c014310(1,0,c)`, `FUN_3c040ff4(7)`, `FUN_3c0457f4(*(ctx+0x2d4),3000)` |
| `2` | reconfigure (mode==1 path) | `FUN_3c014310(2,0,0xff)`, `FUN_3c040ff4(7)`, `FUN_3c0457f4(ctx+0x2d4,3000)`, close `*(u32*)0x20032C88` |
| `4` | incompatible (mode!=1 path) | **`ctx+9 = 4`**, close `*(u32*)0x20032C88` |

The returned code is placed in **ack byte `[2]`**.

**`FUN_3c01c7b0(r0)` / `func_0x3c01c7bc()`** (`0x3C01C7B0` / `0x3C01C7BC`) are a trivial
**get/set pair on global `0x2002A840`**:

```
0x3C01C7B0 :  ldr r3,[0x3C01C7B8=0x2002A840] ; str r0,[r3] ; bx lr   →  *(u32*)0x2002A840 = r0
0x3C01C7BC :  ldr r3,[0x3C01C7C0=0x2002A840] ; ldr r0,[r3] ; bx lr   →  return *(u32*)0x2002A840
```

So `0x2002A840` stores the **peer's config word A** (the `[14..17]` u32): the follower writes
it (`func_0x3c01c7b0(uVar12)`), and the master reads it while configuring its stream
(`func_0x3c01c7bc()`).

**`func_0x3c01ca78(id)`** (`0x3C01CA78`) is a **state predicate**:

```
ldrb r3,[0x2002A82C] ; subs r0,r3,id ; clz ; lsrs #5   →  return (*(u8*)0x2002A82C == id)
```

It reports whether the global state byte `0x2002A82C` equals the argument. The builder uses
it to derive the buf[9] flag: `==3 → 1`, `==9 → 2`.

## Confidence & unknowns

**Confident (disassembly-exact):**
* Payload map: `[2]=mode`, `[3]`,`[4]`,`[5]` option bytes, `[7]=channel/mode byte`,
  `[8]=param_5`, `[9]=state flag (1/2/0)`, `[10..13]=config word B`, `[14..17]=config word A`.
* Channel byte: mode 1 → `2`/`3` from `ctx+0x18`, mode 2 → `4`, else `2`; persisted to `ctx+0x18`.
* **Sample rate = config word B high half = bytes `[12..13]`** (u16 LE, `0xAC44` observed).
* Flag byte from `func_0x3c01ca78(3)`(→1) / `(9)`(→2); `func_0x3c01ca78(id)` = state==id.
* `func_0x3c01c7b0`/`bc` are the set/get of global `0x2002A840` (config word A).
* Role asymmetry: master (`ctx+9==1`) drives the stream object; follower (`==2`) stores config word A.

**Inferred:**
* `ctx+0x18` = channel selector (`2`=L+R, `3`=L, `4`=R per prior live notes); `ctx+0x300`/`+0x301` = mode mirror.
* `0x2002A840` = last received peer config word; `0x2002A82C` = current audio state.

**Unknown / not verified:**
* Exact semantics of config word B's low half (`[10..11]`) and of config word A (`[14..17]`).
* The meaning of `param_2`/`param_3`/`param_4`/`param_5` beyond "option bytes" (only their
  destinations are certain).
* `uRam3c01a548`, `uRam3c01a6a4`, `uRam3c01a6a8` literal-pool globals and the `*puRam` byte
  read in the master branch were not resolved to source semantics.

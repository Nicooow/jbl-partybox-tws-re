# 0x0109 — remote-requested TWS disconnect (application layer)

BESAUD command `0x0109` is the **cooperative "the other side wants to drop the TWS link"**
notification. It carries **no data** (cmd id + 16 zero bytes). It is asymmetric in one important
way: sending it is a request to the peer, but *receiving* it only runs a **partial** reaction
(stop local streaming, flag a teardown, set a link-state code) — it does **not** run the full
local teardown, which is the job of the link-level event-6 path. A live TWS dump shows this is
the message that logs `remote want to  disconnect the TWS`.

* Firmware: `extracted/payload_1.bin` (BES2000IK), Thumb, load base `0x3C000000`. File offset = VA − `0x3C000000`. Aliased at `0x0C000000` (Δ `0x30000000`).
* `ctx = 0x2002F31C` (literal `iRam3c01a508` in `parse_cmd`).
* Frame envelope: `[type][cmd16 LE][payload…]`, type `0x80`=command / `0x81`=ack.
* Evidence status: **static RE only.**

## Wire format

### Outbound — speaker → peer (builder `FUN_3c01afa8`, file `0x1AFA8`)

```c
uStack_1c = 0x109;  uStack_18 = 0;  uStack_14 = 0;  uStack_10 = 0;  uStack_c = 0;
FUN_3c019fe0(&uStack_1c, 0x12, 1000);        /* buf, len=18, wait ≤1000 ms */
```

A pure constant frame — no state is sampled. Wire = **19 bytes**:

| off | size | field | value |
|---|---|---|---|
| 0 | 1 | type | `0x80` (added by `FUN_3c019fe0`) |
| 1 | 2 | cmd16 (LE) | `09 01` = `0x0109` |
| 3 | 16 | payload | `0x00` ×16 |

### Inbound — peer → speaker (handler `parse_cmd` case @ `0x3C01A3F2`)

The handler reads **nothing** from the payload; only the cmd id matters.

```c
case 0x109:
  FUN_3c04cb98(<fmt 0x3C04FD7C>, "tws spp", "tws_besaud_parse_cmd", 0x26e);  /* trace */
  FUN_3c04cb98(0x3C05097C);            /* "remote want to  disconnect the TWS" */
  FUN_3c04cb98(0x3C04D60C);
  FUN_3c018174(5);                     /* set link-state code = 5, run transition */
  *(char*)(ctx + 0x11) = 1;            /* teardown-in-progress */
  if (*(char*)(ctx + 8) == 1)          /* only the "source"/role-1 side ... */
    FUN_3c013310(*(code**)0x3C01A524); /* ... schedules FUN_3c014ea4 via event 0x15 */
  break;                               /* → generic 0x81 ack tail */
```

The string at `0x3C05097C` is confirmed as `remote want to  disconnect the TWS` (note the double
space); the pointer `0x3C01A524` in `parse_cmd`'s literal pool is `0x0C014EA5` = `&FUN_3c014ea4|1`.

**Reply.** The `break` reaches the shared ack tail (`FUN_3c01a08c(buf,0x12)`), so the peer gets the
generic 18-byte `0x81` ack whose first two bytes echo the cmd id; the remaining 16 bytes are stack
remnants on this path.

## Emitted side

The only emitter is the app event loop `FUN_3c012e84` (file `0x12E84`), **event `0x12`**:

```c
case 0x12:
  if (*(char*)(ctx + 8) == 1) {        /* role 1 owns the streaming engine */
    *(char*)(ctx + 0x11) = 1;          /* teardown-in-progress */
    FUN_3c014ea4();                    /* stop/drain the active stream first */
  }
  FUN_3c01afa8();                      /* then send 0x0109 */
  break;
```

So the *initiator* (only if `ctx+8 == 1`) stops its own stream **before** sending, whereas the
*receiver* of `0x0109` sets its flags, sets the state code, and stops its stream (only if
`ctx+8 == 1`). The context guard `ctx+8 == 1` on both sides matches "role 1 = the side that runs
the A2DP/SBC streaming engine". Transmission is still gated by `FUN_3c019fe0` on a live session
(`*(u32*)(ctx+0x310) != 0`).

## Received side — what the reaction does

| step | callee | effect |
|---|---|---|
| log | `FUN_3c04cb98` | prints the trace line + `remote want to  disconnect the TWS` |
| set state | `FUN_3c018174(5)` | stores the value `5` into the global link-state byte reached through the function's literal-pool pointer (`_DAT_3c01819c`) and invokes the state-machine transition callback `(*_DAT_3c04cba4)(_DAT_3c0181b0)`; compare 0x0103's RX-dispatcher path which calls `FUN_3c018174(7)` on SPP drop |
| flag | `ctx+0x11 = 1` | "disconnect/teardown in progress" (same flag set by `FUN_3c014114(1)` in 0x0103, by `FUN_3c0146f8`, and by the event-6 handler) |
| stop stream | `FUN_3c013310(&FUN_3c014ea4)` then event loop | `FUN_3c013310` posts **app event `0x15`** with a 12-byte message `[callback,0,0]`; event-loop `case 0x15` calls `(*(code*)msg[1])()`. The callback is `FUN_3c014ea4`. |
| ack | shared tail | generic `0x81` ack |

`FUN_3c014ea4()` is the **streaming drain/stop**: while `*(char*)(ctx+0x20)` (stream-active flag)
is non-zero it sets `ctx+0x21 = 1`, calls `(ctx+0x3a4)(ctx)` (if `ctx+0x39c`), calls the vtable
entry `(ctx+0x164)(…)`, and yields via `FUN_3c0456a4(1)`; finally `ctx+0x21 = 0`. It is the same
function the emitter calls before sending `0x0109`, and the same one the event-`0x12` guard uses.

**`ctx+0x11`** = teardown-in-progress flag. **`ctx+8`** = current TWS role/state (`1`/`2` are the
live roles set by event-loop `case 0x0D`; `3`/`4` are post-teardown values written by the event-6
handler). The `== 1` guard selects the side that owns the audio path.

## Difference from the link-level disconnect (event 6 → `FUN_3c01abc8`)

| | `0x0109` (application request) | event `6` → `FUN_3c01abc8` (link teardown) |
|---|---|---|
| trigger | inbound `0x0109`, or local event `0x12` to emit it | SPP disconnect (RX dispatcher `case 0x22`), which also does `*(u32*)(ctx+0x310)=0` then `FUN_3c0131d8(6,0,0)` |
| role state | untouched (`ctx+8` unchanged) | `ctx+8` → `3` or `4` (`FUN_3c019600()` picks 3, else 4) and `ctx+9 = ctx+8` |
| objects | none closed | closes three subsystem objects via `FUN_3c04580c`, including `*(u32*)(ctx+0x2f0)` |
| flags | sets `ctx+0x11 = 1`; sets global link-state code `5` | sets `ctx+0x11 = 1` via `FUN_3c014114(1)`; clears event bits with `FUN_3c04101c(4)`, `(6)`, `(3)`; sets `ctx+0x15 = 0`, `ctx+0x308 = 0` |
| streaming | stops the stream (`FUN_3c014ea4`) | stops the stream too (role 1 branch) but also runs the object teardown |
| posts event 6 | **no** | is the event-6 handler |
| clears `ctx+0x310` session | **no** (only the RX-dispatcher `case 0x22` does) | no (same: cleared by the transport path, not by the handler) |

So `0x0109` is a *cooperative notification* ("I am leaving") that makes the receiver stop pushing
audio and marks the link as tearing down and sets state `5`; the actual object/session teardown is
still performed by the transport-level event-6 path. State code `7` (from the SPP drop) vs `5`
(from `0x0109`) is the only observable difference in `FUN_3c018174`.

## Confidence & unknowns

**Confident:**
* Outbound is `80 09 01 | 00×16`; inbound reads nothing from the payload.
* Inbound sets `ctx+0x11 = 1`, calls `FUN_3c018174(5)`, and only when `ctx+8 == 1` posts event
  `0x15` carrying `&FUN_3c014ea4`; it ends with the generic `0x81` ack.
* The emitter is event `0x12`; it stops the stream first only when `ctx+8 == 1`, then always sends.

**Inferred (labelled):**
* `ctx+8 == 1` = the role that owns the audio streaming engine ("source"/master). `FUN_3c014ea4`
  is the streaming stop (its `ctx+0x20` gate is the stream-active flag).
* `FUN_3c018174(n)` = "set the TWS link-state code to `n` and run the transition"; `5` = remote
  requested disconnect, `7` = local SPP drop.

**Unknown / not verified:**
* Who queues event `0x12` (which user/BT condition triggers the *outbound* `0x0109`) was not located.
* The exact global written by `FUN_3c018174` (pointer `_DAT_3c01819c`) and the code pointer
  `_DAT_3c04cba4` were not resolved to concrete RAM/VA.
* Whether the peer is expected to follow up with its own teardown message after `0x0109` is not
  determinable from static code alone.
